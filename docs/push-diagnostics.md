# 手机 Web Push 诊断

创建、追加新题或真正重开题时，服务向主动绑定同名用户名的设备发送 Web Push。交接待办转发微信的功能已于 2026-10-27 退役，不参与手机推送。服务端 `notifyLater` 只在等待用户且未传入测试选项 `disablePush` 时调用发送，生产启动入口不传该选项，也没有对应环境变量开关。

## 可保存的发送证据

每次发送在原请求的私有 `webPushReceipt` 中保存一个最近批次，权限沿用请求文件的 0600。普通网页、公开请求列表和客户端状态 API 不返回此字段。字段包括批次 ID、问题注意版本、开始/结束时间、匹配订阅数，以及以下计数：

| 状态 | 含义 |
| --- | --- |
| `accepted` | 推送服务明确返回 HTTP 2xx；不证明设备接收、显示或本人已读 |
| `rejected` | 明确的 HTTP 拒绝；对应状态码保存在 `httpStatuses` |
| `expired` | HTTP 404/410；沿用原来的设备订阅清理与改绑保护 |
| `unconfirmed` | 网络中断、缺少明确响应或内部异常，不能视为接受 |

`phase:sending` 只表示该批次已开始，进程中断后仍可能保持此状态，不能据此重发。`phase:completed` 表示本批次等待的 Promise 已结束，必须结合各状态计数判断；`deliveryConfirmed` 始终为 false。没有匹配订阅时 `targeted:0`，不把它记作成功。

回执只保存计数、数字 HTTP 状态和固定白名单中的网络错误码；不保存端点 URL、订阅 keys/auth、VAPID 私钥、上游响应正文/headers 或异常 message。过期订阅清理失败单独计入 `cleanupFailures`，不掩盖原 HTTP 结果。Promise 意外拒绝归入未确认，不把目标数量当作成功数量。回执落盘失败保留 `push_receipt_storage_failed` 脱敏日志，不追加发送或重试。

完整批次也写入带 request ID 的 `push_receipt` JSON 日志，发送流程外层异常使用带 request ID 的 `push_dispatch_failed`。后台回执重新读取最新业务记录，只更新自己的批次元数据，保留同时到达的答复、消费游标与完成状态；旧批次不能覆盖新批次。此改动没有增加重试队列或手机回传接口。

旧版本只保留部分 `push_failed`，成功回执及部分过期结果没有保存，不能事后从“没有失败日志”推断成功。新增回执只记录未来实际发送，不回填旧测试或历史请求。

## 订阅与设备限制

现有订阅记录保存用户名、部署路径、最近写入时间 `at` 和订阅证明，没有独立的创建/更新时间、订阅 origin 或订阅时的 VAPID 公钥。API 返回的当前公钥可与服务运行配置作比较，但不能据此证明旧设备使用了相同密钥。排查只导出订阅条数、时间、basePath、推送服务主机等元数据，不能回显完整端点或 keys/auth。

实际显示还取决于手机上的 Service Worker 和系统通知状态。当前 Worker 会过滤未绑定当前用户名、已清空未读、已经同步结束状态的同版本通知，以及重复通知。若先完成请求、手机先同步结束，再收到迟到推送，该通知会被过滤；新一版待答通知仍可显示。仅服务端 finish 不直接关闭手机通知，但可能经页面同步影响迟到通知。

没有设备端状态或新的明确测试授权时，不能判定是哪一项导致未显示，也不能通过重新发送、创建替代事件或使用其他真实请求作验证来补证。已退役微信桥接的历史记录也不能发送或回放。维护源代码、查看元数据和本地合成测试不构成线上发布授权。

## 隔离验证

```sh
node --test test/push-receipts.test.mjs test/notification.test.mjs test/username-push.test.mjs
```

测试使用临时服务、虚构用户数据与替身推送 Promise，不连接推送服务或真实设备。覆盖多种 HTTP/网络回执、零匹配订阅、秘密不进入回执、订阅清理失败、迟到回执保留答案/ack/完成状态，以及 Worker 的结束状态过滤。这些验证不代表手机实际显示问题已解决。
