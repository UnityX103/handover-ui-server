# 远程反馈、求助与交接

使用 sibling [grill-with-ui](../grill-with-ui/SKILL.md) 的本地服务器配置、来源身份、前台等待、回执恢复和事件确认规则；先读该文件。辅助客户端为 `../grill-with-ui/scripts/handover.mjs`，需要 Node 22.11 或以上版本。

每次发起或恢复交接时，共用客户端先检查 GitHub `UnityX103/handover-ui-server` 的 `main`，有新版本则备份并更新两份远程 Skill 后继续。本机需有 Git 与 Node.js 22.11+：以非交互 `git ls-remote` 读取公开仓库 main 完整 SHA，再用 Node 内置 fetch 从 raw.githubusercontent.com 固定该 SHA 下载清单和文件；不需要 gh、GitHub 登录或访问 token。清单校验、并发锁、完整下载、备份、按目录原子重命名切换和失败恢复保持不变，服务器部署身份不变；检查失败时说明并保留现有版本，不重建已有请求。更新显示 `updated:true` 时重读已安装说明；完整行为见 sibling 的“使用前检查更新”。

本地变量 `HANDOVER_SERVER_URL` 指定目标服务器；默认读取权限为 0600 的 `~/.config/handover-ui/config.json`。目标用户通过配置 `username` 或 `HANDOVER_USERNAME` 提供，未配置用户名时始终默认 `Xpy`，无需 Agent token。用户名只是公开分类，不是认证；任何知道用户名的人可能读取或操作其新请求，不能证明答复者身份。旧无用户名记录和 schema 1 handle 仅保留归档，不再在线访问；旧 token 被忽略，旧配置不删除。schema 2 handle 不随配置变化而改归属。

## 选择请求类型

目标服务器地址可以包含 `/handover/` 部署路径；沿用 sibling 的完整地址配置和恢复规则，勿去掉路径或为切换入口重复创建请求。

已经拥有自己的 HTML 审核页面和 JSON 数据格式时，按 sibling 的[自定义页面契约](../grill-with-ui/references/custom-pages.md)接入。先探测能力，远程不可用时保留原 HTML／JSON；收到 `type:"feedback"` 后校验并记录原始 `payload`，再确认消费，不将其当作普通选项答案。

- **feedback**：请本人检查已有内容或结果，给出修改意见。提供实际结果、必要的访问链接、希望检查的方面和可操作的选项。
- **help**：需要本人提供信息、选择方案、处理权限或介入阻碍。说明已完成的工作、实际阻碍、最小需要的动作及对后续工作的影响。
- 多题设计访谈用 `grill-with-ui`。本服务首版只接收 Agent 发起的请求，不从手机创建新任务。
- 需要审核具体代码修改时，在标准问题里提供 sibling 的[代码修改与批准](../grill-with-ui/references/code-review.md)数据：底部列文件、行号与代码，有可展示的效果时先展示，再请本人批准对应版本。保留原任务已有授权，不把普通反馈自动变成改码或发布批准。

## 发起、等待和继续

将请求同时写在当前聊天，创建一个对应的远端请求。可用 `--context` 提供简短背景；需要选项或多题时用与 Grill 相同的 JSON 文件。内容执行 sibling 的“阅读与讨论”：每个 Agent 讨论项先写一句话总结，空行后给可展开的依据；长描述或多步骤关系必须配对应图片或流程图，不用连续长文代替图解。

```sh
node "$SKILL/../grill-with-ui/scripts/handover.mjs" new --kind feedback --topic "请检查这份结果" --context "已完成内容、真实访问链接和需要检查的方面"
node "$SKILL/../grill-with-ui/scripts/handover.mjs" new --kind help --topic "需要你处理的阻碍" --context "已完成工作、具体阻碍和最小需要的动作"
```

上面两个命令是独立示例，每次只按实际需要创建一个请求。保存返回的 handle；创建与恢复请求均不自动打开网页，也不由 Codex 拉起 App。本机“远程交接”App 运行并登录目标用户名后，自行接收新消息并唤起窗口；不要补调 `open`、`home`、系统打开命令或 Codex 浏览器工具，只有本人明确要求手动打开网页时才使用。每次创建或追加待答事项后，立即在来源普通聊天贴出请求的可点击 `url`，同时保留问题与背景；用户名模式保留链接中的 `?username=`，无需密码。浏览器未记住用户名或退出后由本人填写目标用户名，连接成功自动回到原问题。不要只给首页，也不为取链接重新创建请求。用户名模式通过链接在手机处理，并仅向本人主动绑定同名的设备发送 Web Push；旧私有订阅独立，通知不代替聊天中的问题与链接。

来源 Agent 在当前回合使用 `wait --handle … --timeout 25` 分段等待，单次最长 30 秒；超时保持相同请求继续，不能交给后台、其他会话或用通知重新唤醒。只有匹配请求和来源身份的真实答复才解除阻碍。收到后按原文处理，先 patch 记录，再 ack 已处理的连续序号，然后继续来源会话。网页收到服务器保存成功回执后立即返回当前用户名列表，不等待 ack；这不代表 Agent 已处理，列表保持“已发送，等待回复”；通知直接打开对应请求，必要登录后也回到原题。

反馈是意见，求助是人工介入的请求；它们不自动扩大部署、发布、删除、其他会话消息或其他外部操作的授权。若用户只回答部分事项，继续等待或追问剩余必要事项，不能代答。真正结束请求时用 `finish --handle …`；用户取消时可用 `cancel`，保留恢复和已答记录。

恢复命令为 `sessions`、`resume --handle …`、`state --handle …` 和 `pending --handle …`。任何发送结果未知都先核对同一请求，不重复创建，不删除旧回执或跳过未处理事件。

来源 Agent 有权用 `cancel --handle <原handle>` 撤回自己的待答请求。若本人已经在当前聊天作答，或同题群消息答复已明确传回当前会话，先记录真实答复及来源、按需 patch，再取消对应远端问题并继续原任务。仅有群上可能作答的说明不等于收到答案，也不授权另接群机器人或发送群消息。

本人也可在普通问卷或自定义页面点击“取消本次回答”。来源 Agent 收到 `status:"cancelled"` 后停止等待该请求，保留已收反馈、handle 和未处理游标。取消本身不构成答复或实施授权；若必要信息仍缺失，继续保留依赖项，不替用户作答。完整规则沿 sibling 的“本地作答与取消”。
